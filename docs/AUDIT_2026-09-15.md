# Komşu end-to-end implementation audit

Date: 2026-09-15. This audit compares the three-page FıraTech idea PDF, the
40-section engineering brief, the repository, the running local stack and the
latest repeatable checks. It describes a controlled development system. It is
not evidence of field safety or production readiness.

## Executive assessment

The repository is a working vertical-slice prototype rather than a UI mock. A
report can be accepted idempotently, stored with a durable job, analysed,
displayed on the dashboard, reviewed by a coordinator, assigned to a team, and
merged or split with an audit trail. PostgreSQL, PostGIS and pgvector run in the
local Compose stack. The Android application keeps reports and case snapshots
in Room and retries delivery through WorkManager.

Estimated completion, weighted by risk and missing integration work:

- Controlled, presentable hackathon demo: **83–88%**.
- Entire 40-section engineering scope: **50–60%**.
- Pilot readiness with real institutions and field evidence: **25–35%**.

These ranges are engineering estimates, not line-count ratios. Real channels,
validated multilingual data, radio transport, production identity, municipal
data, central operations and external reviews carry more weight than ordinary
feature code.

## Capability map

### Working vertical slice

- Expiring, revocable, hashed bearer sessions; role and tenant checks.
- Strict, bounded report input with a client UUID and immutable source text.
- Atomic report, case, job, audit and event creation before HTTP 202.
- Leased worker processing with retry, stale-claim fencing and idempotent apply.
- Conservative TR/EL/EN baseline suggestions which always require review.
- Human location verification, urgency override and version-checked dispatch.
- Human merge and split with source preservation, version conflicts, history,
  audit and event replay.
- Authenticated REST and cursor-based WebSocket updates.
- Tenant-scoped PostgreSQL schema, forced RLS, PostGIS point storage and
  pgvector report embeddings.
- MapLibre case display, bounded GIS overlays, filters and detail workflow.
- Android Room queue, process-death recovery, WorkManager sync, case cache,
  encrypted token storage and authenticated relay-envelope primitives.
- Reviewed retention plans, expiring legal holds and confirmed destructive
  execution for source text and derived database data.
- Bounded WAV attachment ingestion into tenant-RLS PostgreSQL storage with
  HKDF-separated AES-GCM encryption, keyed replay detection, quarantine state,
  metadata-only API responses and retention deletion.

### Implemented experiments that are deliberately not trusted for decisions

- Pinned local bge-m3 inference and pgvector suggestions. The 240-message
  diagnostic produced recall@1 of 0.0 per language after synthetic identifiers
  were removed; semantic similarity never auto-merges cases.
- Four pinned OPUS-MT routes, including English pivots. The small adversarial
  diagnostic exposed lost numerals, negations and names, so translation is
  disabled by default and shown only with review warnings.
- Pinned local Whisper-tiny inference for approved-root, mono 16 kHz PCM WAV.
  Synthetic TR/EN speech yielded micro WER 0.3793; no Greek, noisy or human
  rescue recording has been validated.

### Prototype-only boundaries

- Channel adapters and webhook signature helpers exist, but no SMS, phone,
  messaging or social provider is connected.
- Geocoding uses a self-hosted adapter contract and fixtures; no approved live
  endpoint or municipal address corpus is configured.
- The web map has case and GIS overlays but no approved base-map package.
- The Android phrasebook contains three TR/EL/EN phrases but no professionally
  recorded audio.
- Relay envelopes, loop prevention, hop limits, custody and cryptography exist;
  Bluetooth/Wi-Fi transport, organisation key distribution and physical
  A-to-B-to-C delivery do not.
- The local benchmark is a 30-report burst on one machine. It does not support
  the 100, 1,000 or 10,000 message-per-second capacity scenarios.

### Pilot and production gates

- Institutional OIDC/PKCE/MFA, gateway-wide quotas, TLS termination and secrets
  operations.
- Central metrics storage, dashboards, alerts, tracing and an exercised on-call
  runbook.
- Off-site backups, repeatable restore objectives, HA/failover and backup/device
  cache re-purge after retention execution.
- Real labelled multilingual messages, native-speaker review, noisy audio,
  address gold sets and calibrated thresholds.
- Municipal GIS and official dispatch/channel agreements.
- Physical Android radio tests, device/OS coverage and offline revocation/key
  rotation procedures.
- Legal review for KVKK/GDPR and cross-border transfer, penetration testing,
  accessibility review, field rehearsal and institutional acceptance.

## Recommended execution order

1. TR/EL/EN dashboard localisation was completed during this audit. Native
   speakers still need to review rescue-domain wording before a field pilot.
2. Encrypted audio quarantine was completed during this audit. Add a malware
   scanning boundary and an explicit release worker before connecting Whisper.
3. Connect one approved geocoder or an offline municipal fixture bundle and
   build the first address gold set.
4. Implement a concrete Android radio transport behind the existing relay
   interface, then validate key distribution and A-to-B-to-C transfer on real
   devices.
5. Run the multilingual, load, failure, privacy, security and field acceptance
   gates before describing the system as pilot-ready.

## Audit conclusion

The former 65–70% demo estimate is stale. The prototype has advanced materially
in database correctness, human control, Android persistence, local models,
retention and operational evidence. The largest remaining risks now sit at the
system boundary: external channels and data, model quality, device radios,
institutional identity, central operations and real-world validation.
